# Prototype
A prototype is throwaway code that answers one open question. The question decides the shape: pick the branch before you build, because getting it wrong wastes the whole exercise.

- "Does this logic / state model feel right?" → a single shareable HTML file, the question stated in a visible intro. **Isolate the answering logic in a pure, liftable module** (a reducer, a state machine, or plain functions, no DOM) chosen by the question; the page is a thin shell over it, and free-play controls plus tabbed guided walkthroughs (each resetting to a known state) push it through the cases hard to reason about on paper. Keeping the logic pure is what lets the validated module lift straight into real code; drivable by a non-developer.
- "What should this look like?" → several radically different UI variations on one route, switchable via a URL param and a floating bottom bar. **Prefer adjusting an existing populated page** over a fresh throwaway route. Make **3 variants** (cap 5), *structurally* different: different layouts, not colours or copy; the switcher cycles with ←/→ (skip when an input is focused), wraps, and is **hidden in production builds**.

If genuinely ambiguous and the user's unreachable, default by context (backend module → logic; page/component → UI) and state the assumption at the top. Build the **cheapest concrete artifact** that settles it: outline, stub, static mockup, rough take. Optimise for reaction, not reuse: no tests, no error handling beyond runnable, no abstractions. Throwaway from day one and clearly labelled as such, sited next to the code it prototypes, trivial to run (one command or a double-clickable file). No persistence by default: surface the full relevant state after every action so the change is visible. Fold only the validated decision into real code; never let a prototype silently graduate into production.

**For UI tickets specifically:** before writing any real UI code, **ask the user whether they want mockups first** (default yes for a new screen). If yes, route by `config.design` (see [Configuration](#configuration)):
- **`disk` (default)**: a throwaway static HTML mockup next to the code, linked from the ticket as an asset (on a throwaway branch, out of main). Fast, self-contained.
- **`claude.ai/design` mode**: create/edit the mockup on claude.ai/design via Anthropic's **official Claude Design MCP** (`claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp`, auth `/design-login` when the session has none), where the user edits it visually. `config.design.surface` picks which surface (unset, a cached `design.project` infers `design-system`, so an existing project keeps its surface; see [Configuration](#configuration)), and on the **first** UI screen for this map you attach to a project; **cache the chosen projectId in the project `.trailhead/config.json` under `design.project`** and **later screens reuse** it. **Link the specific screen** back from the ticket: its own claude.ai/design URL (`claude.ai/design/p/<projectId>/…`), not merely the project.
  - **`canvas` (default)**: a regular design (canvas) project driven by the full Claude Design MCP: the natural home for a one-off screen to react to, editable on the canvas and exportable as a live prototype. On the first screen ask which canvas project to attach to: (a) **pick an existing one**; (b) **paste a `claude.ai/design/p/<id>` URL**; (c) **create a new one**, asking the user first for its name (don't invent it). Later screens are added to the same project.
  - **`design-system`**: push the mockup as a component into a **design-system project** via the **`/design-sync` skill + `claude-design` MCP (DesignSync)**, the design-system slice of the same official MCP, for a shared component library kept in sync. On the first screen, three paths: (a) **pick an existing one**, listing the **10 most-recently-updated** design systems from DesignSync `list_projects` (sorted `updatedAt` desc); (b) **paste a URL**, taking the projectId from a `claude.ai/design/p/<id>` link and confirming with `get_project` that it's a `PROJECT_TYPE_DESIGN_SYSTEM`; (c) **create a new one** (name from the user), then `create_project`. Later screens reuse it (`finalize_plan` → `write_files`). **DesignSync only targets `PROJECT_TYPE_DESIGN_SYSTEM` projects**: verify with `get_project` before pushing; a regular `PROJECT_TYPE_PROJECT` **cannot** be driven by DesignSync, so use the `canvas` surface for one of those.
  - **Missing MCP: offer to install it once, don't degrade silently.** When `design: claude.ai/design` is configured but the MCP the chosen surface needs isn't connected (the full Claude Design MCP for `canvas`, DesignSync for `design-system`), **surface the enable steps once** before falling back: `claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp`, then `/design-login`. Let the user **install-and-retry or decline**; never auto-install. If they install and it connects, use the configured surface. If they decline (or it still doesn't connect), fall down the chain below and **don't re-offer for the rest of the session**. This is a one-time **infrastructure** prompt, **orthogonal to `design.approval`**: `auto` only skips the wait on *mockup* approval, it never silences the install offer (an MCP can't be auto-installed), though a decline degrades without blocking, in keeping with `auto`.
  - **Fallback chain** once the offer is declined or doesn't apply: `canvas` needs the full Claude Design MCP connected; if it isn't but DesignSync (design-system) is, offer the design-system surface or `disk`; if neither is available, `disk`, and say so. **On a host without the Claude Design MCP (e.g. Codex, which has no `claude-design` MCP or `/design-sync` skill), `claude.ai/design` mode isn't available.** Because **`stitch` mode is cross-host** (below), don't degrade silently there: **offer once to switch this project to `design: stitch`** (with the Stitch install offer if its MCP isn't connected), and only on decline fall back to `disk`. Offer this once per session; on decline, don't re-ask. (On Claude the three modes stay independent explicit choices, no auto-redirect between them.)
- **`stitch` mode**: create/edit the mockup via the **Google Stitch MCP** (`https://stitch.googleapis.com/mcp`), Google's Gemini-powered UI generator. Unlike `claude.ai/design`, the Stitch MCP is a standard HTTP MCP that runs on **both Claude Code and Codex**, so it's the **cross-host** hosted option. `config.design.surface` picks the surface (the same key as claude.ai/design), and on the **first** UI screen for this map you attach to a Stitch project; **cache the chosen projectId in the project `.trailhead/config.json` under `design.project`** and **later screens reuse** it. Because `design.project` is shared with `claude.ai/design`, **verify the cached id belongs to Stitch (`get_project`) before reusing it**, and re-attach if it doesn't. **Link the specific screen** back from the ticket.
  - **`canvas` (default)**: a Stitch project with generated screens to react to: `generate_screen_from_text` for the first screen (or `generate_variants` for structurally different alternatives), `edit_screens` to refine, `get_screen` / `list_screens` to read back. On the first screen ask which Stitch project to attach to: (a) **pick an existing one** (`list_projects`); (b) **paste a project URL**; (c) **create a new one** (`create_project`, name from the user, don't invent it). Later screens are added to the same project.
  - **`design-system`**: push the mockup into a **Stitch design system** (`create_design_system` / `create_design_system_from_design_md` / `apply_design_system`, read/update via `list_design_systems` / `update_design_system`) for a shared component library. On the first screen: (a) **pick an existing one** (`list_design_systems`); (b) **paste a URL**; (c) **create a new one** (name from the user). Later screens reuse it.
  - **Missing MCP: offer to install it once** (the same rule as claude.ai/design): if the Stitch MCP isn't connected, surface the enable step once, `claude mcp add --scope user --transport http stitch https://stitch.googleapis.com/mcp` (authenticate if prompted), and let the user install-and-retry or decline; never auto-install. On decline (or a still-missing MCP), fall back to `disk`, and say so. There's no intra-provider chain: the Stitch MCP either connects or falls to `disk`. One-time infrastructure prompt, **orthogonal to `design.approval`** (see above).

Either way the rough screen is **reacted to before real UI code**. How approval gates the build depends on `config.design.approval`:
- **`explicit` (default)**: surface the mockup and **wait for the user's clear go-ahead**; do not write UI code until they approve. Record the approval on the ticket, then proceed.
- **`auto`**: surface the mockup and **proceed without blocking** on a confirmation (the user can still object). Record the direction on the ticket.

**In `claude.ai/design` mode, re-fetch the design before you build on it.** Between surfacing the mockup and writing the UI code the user may have edited it directly on claude.ai/design, so once it's approved (or, in `auto`, right before you consume it), pull the **current** state from the project via the Claude Design MCP (on the `design-system` surface, `list_files` → `get_file`) and build from *that*, never from the version you last pushed. Note on the ticket that the design was re-fetched at that point.
