# Research

**First, route it.** Run `node <hooks>/lib/model-route.js research --session <your full model id> <project root>` and obey its `route`. Your full model id is in your system prompt or environment ("The exact model ID is ..."); pass `unknown` only if it is truly absent. Obey it exactly: never decide inline versus dispatch by hand, never read the config yourself to decide. On `route: dispatch` spawn the `agent` it returns with model `alias` (`agent_type=<agent>` on Codex) and use its report; on `route: inline` run the protocol below in the session. Finding `<hooks>`, the flags and the two exceptions are in **Route every step through model-route.js** in `../techniques.md`. (If you are the `trailhead-research` agent, skip this gate: you are the dispatched step.)

Spawn a focused subagent (AFK, parallelisable) with exactly ONE clear question: sharp enough that the answer is a decision, not a survey. Vague scope breeds rabbit holes; a narrow question is its own leash. On `route: dispatch` it is the **`trailhead-research`** agent (it commits nothing and creates no branch: the report is the artifact), with the route's `alias` as the model override; route once, then reuse it for every parallel question; **never** an external-plugin researcher agent that another installed tool registered.

- **Treat your own prior knowledge as hypothesis, not fact**: training is stale. "As of my training" is a warning flag, not a citation.
- **Chase primary, high-trust sources**: official docs, source code, specs, first-party APIs; never a secondary write-up. Follow every claim back to the source that owns it; resolve *current* docs rather than reciting from memory.
- **Verify before asserting.** Cross-reference critical claims across sources: official docs (primary), release notes (currency), one more (confirmation). Check version numbers and dates.
- **Guard the classic traps:** a negative claim ("X isn't possible") needs official verification, not a failed search; "didn't find it" ≠ "doesn't exist"; old docs may describe a deprecated path (check the changelog); verify ALL config scopes before ruling one out.
- **Distinguish verified fact from inference explicitly.** Assign honest confidence (LOW when only training data backs a claim). "I couldn't find X", "sources contradict", "LOW confidence" are valuable findings, not failures; never hide uncertainty behind confident prose.
- **Investigation, not confirmation:** gather evidence, then conclude; don't start from the answer you want and collect support.
- **Stop at sufficiency; no redundant re-reads.** Once the evidence is decision-ready, conclude: gathering past a confident answer is analysis paralysis, not rigour. Don't re-open a source you have already extracted from in this pass (re-reading the same file to re-derive a fact you already hold); cross-referencing a *new* source for confirmation is different, and still required.
- Return a **decision-ready answer** (verdict, tradeoffs, confidence, citations), not a raw data dump, as the agent's investigating report (`Return contract` in its definition): `answer:` holds the verdict, tradeoffs and confidence; `evidence:` holds every claim with its source URL; `open questions:` what stays unsettled. No branch, no committed artifact: parallel research agents share one checkout, so the report is the artifact.

**Report (orchestrator).** Run the report-status check on each report (`--technique research`, the *Malformed review report* protocol in `../techniques.md`) and branch on the checker's `verdict`, reading its `fields`. Post the report as a `RESEARCH` comment on the research ticket (every claim with its URL in `evidence:`). `status: found` -> post, then resolve the ticket. `status: inconclusive` -> post, then ask the user: accept the answer at that confidence, narrow the question, or run another round. `status: needs_input` -> ask the user the `open questions:`, then re-spawn with the answers.
