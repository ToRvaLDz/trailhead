# Acceptance testing
Automated tests prove the code does what the *code* intended; acceptance testing proves it does what the *user* wanted. After tests + code review pass, decide whether the change needs acceptance testing (user-facing behaviour usually does; a pure refactor or internal util usually doesn't) and pick the cheapest sufficient path:

- **Automated first, but it does NOT discharge acceptance for user-facing behaviour.** Run the ticket's test/criterion and the suite. Passing tests prove *code-intent*; they close acceptance only for a change the user never sees (refactor, internal util). For anything the user perceives (a new screen, data that now appears/updates, a changed flow) automated green is *not* "done": you still owe the drive-mode ask below, then a browser-drive, AI-driven checks, or a guided UAT, unless the user explicitly skips (waives) acceptance there.
- **Stale-base preflight comes first.** A UAT never runs on a base that is behind the trunk or whose project checks fail (`trailhead-base-preflight.js`, **Stale-base preflight** in `../teamwork.md`). Inside `build`/`bug` Verify the preflight already ran at the start of Verify, which covers this ask; on the other start paths (Pending-UAT option (a), a `UAT of:` follow-up) run it before the drive-mode ask.
- **UAT setup comes next.** At all three start paths (`build`/`bug` Verify, the Pending-UAT guard's option (a), a `UAT of:` follow-up), after the stale-base preflight and before the drive-mode ask, bring the target up with `trailhead-uat-setup.js`, whichever mode then drives (most real UATs are human-driven, on-device). The drive-mode ask wording is unchanged. Config: `uat.setup` / `uat.accounts`, **UAT setup** in `../configuration-reference.md`.
  - **Run it.** `plan` first (`--repo <working-root> --config-root <original checkout>`): it lists the steps, their `note`s and which referenced `$ENV` variables are set, never a value. Honour each step's `note` before running it, and ask the human when the note says to. Then `run`; it skips a step whose `check` passes and stops at the first failure. Branch on `status`, fail closed: only `ready` and `none` go on to the drive-mode ask; `unconfigured` goes to the probe below; `invalid` and `failed` stop.
  - **Failure.** Stop and report the failing step with its output (a `missing-env` names the variable), then ask: **retry**, **the human does that step**, or **proceed without it** (the UAT steps that depend on it become explicitly pending and tracked, per the partial-run rule). When the output implicates the ticket's own code (its build or deploy fails), also offer **treat as a defect** (fix on the ticket, or a `bug`). Never a silent fallback. The output is a redacted tail, a best-effort backstop: read it before showing it and redact anything credential-like.
  - **Unconfigured project** (`status: unconfigured`). Probe the project (package scripts, Expo/adb, docker compose, Supabase functions/migrations, an already-running server), **propose** the setup plan, run it on an explicit yes, then **offer to save** it to `uat.setup` in the original checkout's `.trailhead/config.json`, replacing machine-specific values with `$ENV` references and naming the variables to set. Nothing plausible found: ask the human what setup is needed (same save offer). A declined save offers to write `[]`; declined again, it is not re-offered this session. `[]` (`status: none`) means no setup needed: no probe, no offer.
  - **Accounts.** Pick the `uat.accounts` role matching the step, ask when ambiguous. References resolve only inside tool inputs (a browser field, a command's environment), never into chat, issue comments or commits; in human-driven mode show the user and the reference name only.
  - **Record.** What ran, was skipped or failed goes in the `VERIFY` comment: step names and results only, never output or values.
- **Drive mode: ask who drives the UAT.** Every UAT start puts one explicit ask to the human, **before any step runs**: AI-driven, human-driven, or *skip (waive acceptance)* (plus the standard delegate option, per `../choices.md`; no defer, this is now-or-never at UAT start). It fires at three start paths: `build`/`bug` Verify, when acceptance testing is owed; the Pending-UAT guard's option (a) (run the UAT now); and resolving a UAT follow-up (any ticket carrying `UAT of:` in its body). The ask must **wait for an explicit answer**: **silence or an ambiguous reply re-asks**, it never defaults to a mode or to skip. Never fires when acceptance is not owed.
  - **One-path skip**: a step is agent-performable unless it needs something the agent cannot access this session: a physical device or hardware it cannot reach (none connected, no tool to drive it), credentials or accounts it does not hold, or a human sensory judgement (feel, sound, haptics, subjective look), evaluated over the checklist before asking. No step performable: the ask drops only the AI-driven option and asks **human-driven or skip**, and **states the reason in one line** (naming the blocking class) before asking; on this reduced ask the delegate option resolves to human-driven (never skip). Any step performable: ask with all the options.
  - **AI-driven.** Per step: browser-drive when drivable (the URL resolution below); else drive the device the session can reach (a phone or emulator over `adb`, an iOS simulator, a TV, a desktop app, through the connected tools: a device MCP, computer use, the platform's CLI), with a screenshot as evidence; else commands, the suite, or scripted checks; record each result and its evidence as it goes, gathered for part 3 of the round's single `VERIFY` comment (layout in *Malformed review report* in `../techniques.md`), which the orchestrator posts once the round's checks, including this one, are done (on the two start paths outside a Verify round, the Pending-UAT guard's option (a) and a UAT follow-up, there is no round: the orchestrator posts the results as a `VERIFY` comment of their own once the UAT ends); ask the human only for the steps it cannot perform, one at a time, conversationally, exactly like the guided walkthrough below.
  - **Skip (waive acceptance).** Offered at all three start paths. A skip is a **waiver, not a deferral**: the user forgoes acceptance, so nothing is left owed. Record `acceptance: waived by the user (unconfirmed)` in the `VERIFY` comment (part 3 of the round's single `VERIFY`, or a standalone `VERIFY` comment on the Pending-UAT guard's option (a) and UAT-follow-up paths, which have no round), never a pass. No step runs, no follow-up is opened, and the Pending-UAT guard does not fire. The resolution comment states the waiver. On a `UAT of:` follow-up, a skip closes as waived: the resolution comment links back to the parent and states the waiver. The delegate option never picks skip and `auto` never picks skip: waiving acceptance is the human's call.
  - **Human-driven.** The guided conversational walkthrough below runs unchanged: one step at a time, wait for the human's report, never a checklist to self-serve.
  - Applies **in both modes**: the failing-step handling, the partial-run / pending tracking, and the mockup-fidelity check below apply the same way, whichever mode drove the run.
  - **Config.** `acceptance.browser: off` disables browser-driving, not AI-driven checks run via commands or the test suite, and it does not pre-answer this ask or imply a waiver (only the human's explicit skip waives acceptance): the ask still fires, and an AI-driven answer still runs its non-browser checks.
  - **`auto` takes this ask as the delegate option without the confirm gate** (per `../choices.md`): AI-driven when any step is agent-performable; human-only steps stay incomplete and the ticket is set aside, listing them in the run-end summary (never faked); no performable step means the whole UAT is human-only and the ticket is set aside. Full autonomous-run behaviour lives in `../../trailhead-work/references/auto.md`.
- **AI-driven, browser-drivable web app → drive it yourself.** Governed by `config.acceptance.browser` + `config.testing`: when it's `auto`/`on` and `testing.webapp` is set with `testing.url` set or resolvable (see below), use the browser-automation tools to exercise the actual change end-to-end (navigate, fill, click, assert visible state; capture a screenshot as evidence for part 3 of the `VERIFY` comment). Prefer this over asking the human when the flow is scriptable. Never trigger native/JS dialogs that would wedge the session.
  - **Auto mode resolves the URL before falling back.** Under `acceptance.browser: auto`/`on`, when `testing.webapp` is set but `testing.url` is not, do not drop straight to asking: first try to determine the target URL from the project. Probe, cheapest first, a dev server already running (the likely local ports, or a server log / PID the project writes), package scripts (`dev`/`start`/`preview` in `package.json` or the project's task runner), dev-server and framework config (the configured host/port in e.g. Vite/Next/Astro/Expo config), and project config. When one is found, **propose it** ("acceptance will run against `http://localhost:5173`, correct?") for the user to accept or correct, then drive the browser against the accepted URL. Only when no URL can be determined fall back to asking the human, or to the guided UAT below.
- **Human-driven, or an AI-driven step that isn't performable → guided UAT is MANDATORY, and it is CONVERSATIONAL.** This is the human-driven mode from the drive-mode ask above, and it is also what an AI-driven run falls back to for the specific step(s) it cannot perform: when `config.acceptance.browser` is `off`, or no target URL could be determined (the auto attempt above included), or the target can't be driven this session (a device or hardware the session cannot reach, real credentials it does not hold; a mobile/native app or a TV on a connected device or emulator *is* drivable, per the AI-driven rule above), **`off` means "acceptance via a guided walkthrough," not "skip acceptance."** For any user-facing change you MUST **run the human through the UAT one step at a time, in the chat**: state step 1 (what to do, where to tap/look, the expected result), then **stop and wait** for the human to report what they actually saw; only then move to step 2. It is a dialogue *you* drive, turn by turn, not a list you hand over. **Anti-pattern, never do this:** post the full numbered checklist and point the user at the ticket to self-serve ("follow the 9 steps in the comment of #NN"). That is exactly the failure this rule kills: the checklist is the *record*, never the *interaction*. Mirror each step's outcome into the `VERIFY` comment as you go; don't close on green you didn't actually see.
  - **On a failing step: stop, take note, open the closing ticket then and there.** A failed step is an acceptance finding, not a footnote: record expected-vs-seen, and immediately open the follow-up that will carry it to resolution: a `bug` ticket (with `Regression of:`/`Surfaced from:` as fits), or a fix on this ticket before it resolves if it's small and in-scope. Then ask the human whether to keep going through the remaining steps or stop here. Never silently log a fail and carry on to Resolve.
  - **When only some steps are runnable now** (e.g. a few need a backend deployed first), walk the runnable ones conversationally **now**, and mark the rest **explicitly pending** with what unblocks them, tracked as below. Don't defer the whole UAT just because part of it is blocked.
  - **When the human can only run it later** (on-device, hardware you don't have right now), record the full numbered checklist in part 3 of the `VERIFY` comment as the durable artifact and mark UAT **explicitly pending**, but the walkthrough stays conversational **when they come to run it**: never shrink it to a vague one-liner ("just check it on the device"), and never let "automated passed" quietly stand in for it. Deferring *where/when* the human runs it is fine; replacing the live step-by-step with a self-serve checklist is not.
  - **Pending UAT must stay tracked: a closed ticket is not tracking.** Don't resolve/close a user-facing ticket on unconfirmed acceptance by your own choice and leave the checklist as a comment on the closed issue, where nobody will look. The one exception is an explicit waiver: **a waiver is not a deferral**. The human picked skip at the drive-mode ask and forwent acceptance, recorded as unconfirmed in `VERIFY`, so nothing is owed and nothing is opened. The default is otherwise to **keep the ticket open** until the human confirms the UAT passes (closing on green you didn't see is a premature close). **When UAT hasn't been run at Resolve, pose the choice to the human and wait for an explicit answer, never decide it for them:** (a) **run the UAT now**, in this session, with no ticket (opens with the drive-mode ask above, then the guided conversational walkthrough or AI-driven checks, resolving on a confirmed pass, or on an explicit waiver if the user skips at the ask (recorded as unconfirmed; the resolution comment states it); a failing step becomes a fix or a `bug` follow-up and an incomplete/blocked step is marked pending and tracked, per the failing-step and partial-run rules above, never a silent close), or (b) **open a UAT ticket** to run it later. **Never open a UAT ticket without asking, and never let silence or an ambiguous reply default to either path.** Only when the human picks (b) do you **open a follow-up ticket before that close** that carries the pending UAT and links back to the parent with a `UAT of: [<parent name>](<parent url>)` pointer line in the body, and carries the `trailhead:uat` label: put it in the `--label` list of the `gh issue create` (next to the `trailhead:ticket` and type labels), ensuring the `trailhead:uat` label idempotently first (`substrate-commands.md`). Route it the way `../choices.md` routes a deferred choice: a **`trailhead:seed`** (kept blocked) when the run is gated on a future external trigger not yet true (hardware you don't have, a device out of reach), or a follow-up **`task`** on the frontier when it's just scheduled or batched work you could pick up any time. Either way the follow-up **carries the full numbered checklist and, when it comes to resolution, opens with the drive-mode ask above before running the guided conversational walkthrough**, never a self-serve check-off. **Never close a user-facing ticket on a chosen-deferred UAT with nothing opened**: the parent may close as agreed, but the owed UAT stays visible on the tracker as its own ticket, linked to the parent, until it is actually performed. The pending check must be visible on the tracker, not buried.

**Mockup-fidelity check (when the ticket had an approved mockup).** If the change was preceded by an approved mockup (the **Prototype** technique produced one and it was approved and recorded at Execute), acceptance testing MUST check the built screen **against that approved mockup**, not merely against "what the user wanted" in the abstract. Pull the mockup's current state to compare against (re-fetch it in `artifacts` / `stitch` mode via the technique's re-fetch rule, or open the linked `disk` mockup); never compare from memory. Walk it **element by element and state by state**, layout, spacing, sizing, colour, typography, copy, and every state it shows (empty, loading, error, hover, active, disabled, and the like), enumerating from the approved mockup itself (the spec) and cross-checking the executor's recorded Execute-step fidelity list and any element it flagged infeasible, and confirm each is reproduced. Record the per-element and per-state result in the `VERIFY` comment. Any **unforced** deviation is an acceptance finding, never waved through as "close enough"; a genuinely infeasible part must already have been raised with the user at Execute (per the Prototype technique), not surface here as a silent drift.

Acceptance failures are findings like any other: a `bug` follow-up or a fix on this ticket before it resolves.
