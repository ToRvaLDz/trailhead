# Working as a team

Many people (and their agent sessions) share one map and work it concurrently. The tracker is the single source of truth; these conventions keep concurrent work from colliding.

## Claiming
Whoever claims a ticket **owns it end to end**: they work it and close it themselves. "Owner" means only "the current claimer of *this* ticket," never a project-wide approver; there is no gate and no one to wait on to close your own ticket. GitHub assignment isn't an atomic lock, so keep the protocol simple and human-decided:

1. **Before claiming, check it's not already being worked.** Read the assignee. **trailhead runs as the user's own gh account, so `@me` is the user's login:** a ticket assigned to that account is **already yours**, so proceed silently to work it (this is the normal "continue / resume your own ticket" case), don't re-announce the claim or treat it as a collision. Only a **different** login means in-progress-by-someone-else: don't take it; pick another frontier ticket. (If the user explicitly named a ticket held by another login, stop and tell them it's assigned to `<login>`; if they named one already assigned to their own account, just work it.)
2. **Claim it**: assign it to yourself: `gh issue edit <n> --add-assignee @me`.
3. **Re-check right before starting work.** Read the assignee again. If someone else got assigned in the meantime, **do not do any work, stop and flag it to the user with a clear message**, e.g.:

   > ⚠️ **Claim collision on “<ticket name>” (#<n>).** It's now also assigned to **@<other-login>**, who may be working it right now. I've stopped and done nothing. How do you want to proceed?
   > 1. **Leave it to them**: I'll unassign myself and take the next frontier ticket.
   > 2. **Take it over**: I'll keep it and post a comment notifying @<other-login> that you're taking it.

   Do exactly what the user chooses; never resolve the collision silently.
4. **Unclaim if you stop.** Abandoning a ticket → remove your assignment so it returns to the frontier. Pausing it open-endedly → remove your assignment too, but it stays off the frontier (`trailhead:paused`) until someone takes it back with `/trailhead:resume` or a named `work <n>` / `quick <n>`. A claimed-but-idle ticket is invisible work.
5. **Never touch a ticket someone else holds.** Don't edit its body, labels, or state; contribute via a comment and let its owner incorporate it.

## Isolating concurrent sessions
Claiming stops two sessions from working the *same* ticket; it does nothing about two sessions working *different* tickets in the **same checkout**. The working tree and the git index are process-global: two agents editing and committing in one clone corrupt each other's state regardless of ticket type (a `bug` is no more or less exposed than a `build`). The claim is the ticket-level lock; the **worktree is the filesystem-level one**.

The repo's `trailhead:conventions` `isolation:` header decides:
- **`auto`** (default): resolve the mode at a ticket's **work-start, before any edit**. First run a read-only, best-effort **assigned-ticket pre-check** to inform (never decide) the ask: `gh issue list --assignee @me --state open --json number,title,body`, then drop the current ticket's own number from the result (the claim precedes this resolution, so the current ticket is already assigned to `@me`, and must be excluded or the pre-check always sees a false "other"); on any `gh` error skip the pre-check and put the ask neutrally rather than failing the work. An assigned ticket is a **heuristic** for concurrent work, never proof (it may be a live parallel session or a parked/paused claim). **0 other assigned tickets**: put the ask neutrally, as below. **One or more other open assigned tickets**: **pre-bias** the ask, name the already-assigned ticket(s) and default the answer toward *yes* (`worktree`/`clone`), but **still ask**, with an easy neutral/no; a ticket whose `Scope:` is absent is presented as *overlap unknown*, never as evidence of safe concurrency. **Skip the ask entirely only in the one unambiguous, self-referential case**: the session is already inside **this** ticket's linked worktree, that is all of (a) `git rev-parse --git-common-dir` differs from `git rev-parse --git-dir` (a linked worktree), (b) the checked-out branch is exactly `trailhead/t<N>` with `N` equal to the current ticket number, and (c) the working-root `.trailhead/session-ticket` marker names the current ticket; then isolation is already this ticket's operating mode, so resolve to that worktree and announce it without asking. A per-ticket **clone** is deliberately **not** a skip trigger (no reliable read-only predicate separates a dedicated clone from the primary checkout switched onto a `trailhead/t<n>` branch), so it takes the pre-bias-and-ask path. This pre-check is read-only and changes no `worktree`/`clone` mechanic, and **scope overlap with another in-progress ticket is out of its remit** (the existing serialise / undeclared-coupling handling owns that). **Remembered answer (reuse).** After the self-referential skip (which keeps precedence and never reads or writes the record), and using the pre-check's list of other assigned tickets as the fingerprint, run `node <templates>/trailhead-isolation-answer.js check --repo <project root> --others <csv|none|unavailable>` from the checkout the session started in, before any workspace is set up (`<csv>` the other assigned ticket numbers, `none` when there are none, `unavailable` when the pre-check failed, which always re-asks). It prints one JSON line. On `status: reuse`, print one line naming the reused answer (e.g. "Isolation: reusing this session's answer (one ticket at a time); say so to change it" for `no`, "(several tickets at once, isolated workspace)" for `yes`) and resolve exactly as that answer would, without asking. On `status: ask` (reason `absent`, `expired`, `claims-changed`, `invalid` or `unavailable`) or `status: skipped` (an I/O error: treated as ask), do the pre-bias and the ask below, and **only after the user answers** run `node <templates>/trailhead-isolation-answer.js record --repo <project root> --answer yes|no --others <csv|none>`, which replaces the previous record. The record is the gitignored `.trailhead/isolation-answer.json` at the project root (add it to that repo's `.gitignore` if absent, like the session-ticket marker; inside a linked worktree the helper resolves to the main checkout, so every worktree reads the same record). A *session* here is a working stretch on this machine, not a conversation (a conversation holds one ticket, `/clear` between tickets): it lasts while work-starts keep coming and ends after **8 hours** without one (a sliding idle window; each reuse refreshes it). The answer is reused only while the live claims are unchanged: the same set of other assigned tickets (a parallel claim appearing, a paused claim lingering or a claim released all re-ask). A user who says to change the answer is re-asked and recorded. `<templates>` is found with the same three-dir lookup as `trailhead-work-state.js` (see **Work state file**); a missing helper or a non-zero exit means ask as before, silently. `/trailhead:auto` and an explicit `none`/`worktree`/`clone` never read or write the record. Ask once whether more than one ticket will be worked at once on this machine this session (this **is** the `clone` gate below, generalised to the whole mode, so a `clone` resolution never re-asks). **No** (a lone ticket): work in the current checkout, exactly like `none`. **Yes**: resolve by repo shape, a plain repo -> `worktree`, a **superrepo** (a `.gitmodules` at the checkout root that declares at least one submodule; equivalently `git submodule status` lists one) -> `clone` (the superproject clone + submodule provisioning below). Because trailhead resolves **one ticket per session**, the ask fires at most once per ticket work-start, and a remembered answer (above) may suppress even that while the claims are unchanged within the 8-hour idle window; the autonomous run (`/trailhead:auto`) **never asks** and never runs the pre-check; it resolves `auto` to the current checkout with one parallel slot and to a worktree per ticket above one (see `trailhead-work/references/auto.md`). `auto` is a **runtime interpretation**: the engine never writes `isolation: auto` into the conventions.
- **`none`**: one session at a time per checkout. Simplest, and correct for a repo worked one ticket at a time. Two concurrent sessions here must use **separate clones**, or they collide.
- **`worktree`**: each executing ticket runs in its own `git worktree` on a `trailhead/t<n>` branch (`git worktree add ../<repo>-t<n> -b trailhead/t<n>`), so concurrent sessions never share a working tree or index. Because git refuses to check out one branch in two worktrees, **worktree isolation implies a branch per ticket even under `git: main`**: the trunk is never checked out twice. At **Resolve**, integrate the branch to the trunk per `git:` (fast-forward or merge into `main`, or open the PR when `git: pr`), then `git worktree remove` it. On **Pause**, the `PAUSED` checkpoint records the worktree path and branch so a resume (by anyone, once released) lands back in it. An autonomous run with parallel slots uses this layout (a sibling worktree per ticket) through the `trailhead-auto-slot.js` helper.
- **`clone`**: each executing ticket works in its own **independent working copy** at `../<repo>-t<n>` on a `trailhead/t<n>` branch (for a submodule-bearing superrepo the clone is of the **superproject** with `--recurse-submodules`, never the submodule alone, so the gitlink bump has a home and each ticket gets independent submodule state; see **Git submodules force `clone`** below). That is the point: it has its own installed dependencies, so it **builds and UATs like the real thing**: the isolation for **path-bound apps a worktree can't run** (React Native/Expo, native toolchains, a local `node_modules`). **A clone is heavy (a full clone + an install), so gate it every time: before cloning, ask whether more than one ticket will be worked at once on this machine this session. If not, skip the clone and work this ticket in the current checkout** (isolation only guards concurrent workspaces; a lone ticket has nothing to collide with). If yes, set it up at work-start by **whichever is faster**:
  - **`git clone` + the project's install step** (clean git; pays the install cost; add `--recurse-submodules`, or follow with `git submodule update --init --recursive`, when the repo has submodules so nested ones are provisioned too), or
  - **a folder copy that brings `node_modules`** (`cp -r` the repo or superproject, submodule working trees included) to **skip the reinstall**, usually faster for a big `node_modules`. **Catch (git independence):** a raw copy can leave the copy's `.git` (or a submodule's `.git` file) pointing back at the **original**, so its commits would leak there. Verify with `git -C <copy> rev-parse --absolute-git-dir` **and the same inside every submodule (nested included)**: each must resolve **inside the copy's own tree**, not the original or another ticket's copy. If any points outside, re-point it, or use the `git clone` route and copy only `node_modules` across.

  At **Resolve**, push the branch and integrate per `git:` (into `main`, or a PR); for submodule changes follow **publish-before-point** in **Git submodules force `clone`** below (push or merge the submodule commit first, only then bump the superproject gitlink), because the clone is disposable and a gitlink must never reference a commit that lives only in it. Record the copy's path in the `PAUSED` checkpoint and delete it once integrated.

  **Gitignored files in a new workspace.** A fresh worktree or clone has none of the gitignored files the app needs to run (`.env`, local config). They are declared once per project in the `isolation.copy` key of `.trailhead/config.json` (see `configuration-reference.md`, **Isolation copy**). **Immediately after creating the worktree or clone, and before any install or build step** (an `.npmrc` or local config may be an install prerequisite; for a folder-copy clone the files are already there and simply report `present`), run `node <templates>/trailhead-isolation-copy.js --from <main-checkout> --to <working-root>`, with the same three-dir `<templates>` lookup as the commit-msg sync above. Never for `none` (nothing is created). It prints one JSON line `{status, copied, present, missing, rejected, suggestions, warnings, message?}` and never overwrites an existing file. Report one result-oriented line naming what was copied, naming any `missing` entries so the user can create them, any `rejected` entries (unsafe paths discarded from the declaration), and surfacing any `warnings`; stay silent on `nothing` only when `missing`, `rejected` and `warnings` are all empty. A `status: skipped` is reported like the missing-script case (one line, nothing copied, move on). On `unset` with `suggestions` (tracked `*.example` / `*.sample` files whose stripped sibling is gitignored in the main checkout), offer once, as an `AskUserQuestion` menu (delegate allowed), to set `isolation.copy` to them. On yes, write the key in the **original checkout's** `.trailhead/config.json` (config writes never target the workspace, per `configuration.md`), commit that one file there on the trunk as `chore: declare files copied into isolation workspaces` with the ticket's `Refs: #<n>` trailer, so the declaration is shared once per project and never lingers as an unrelated dirty change; if that file already had other uncommitted edits, leave the write uncommitted and tell the user in one line. Then re-run the copy. On `unset` with no suggestions stay silent; on `invalid`, one line naming the config problem and no offer; on a missing script or a node error, one line that nothing was copied, and move on (it never blocks the work). A resumed workspace re-entered on resume needs no re-run (the files are already there).

With the default `auto` this choice is made for you at each ticket's work-start; set `worktree` explicitly to force an eager worktree regardless. Prefer `worktree` whenever more than one session may run on a single clone. On a **monorepo** it is doubly worth it: `git worktree add` shares the object store, so it is far cheaper than a second full clone of a large tree.

**If the header never set `isolation:` at all**, it resolves to **`auto`** (the default) at runtime: the work-start concurrency ask decides the mode by repo shape (above), and **nothing is written** into the conventions. This supersedes the earlier behaviour where an absent key silently meant `none` with a one-time collision sanity-check that wrote a key; that nudge-and-write flow is **gone**. A header that already carries `isolation:` (any value, including `none` or `auto`) was chosen deliberately and is honoured as-is.

**Stale-base preflight.** A UAT run on a base that is behind the trunk tests the wrong code, and a merge that is textually clean can still break the trunk. So the engine measures the base, syncs it, re-runs the tests and runs the project's own checks before UAT and before integration, in this order. In Verify: preflight -> sync -> checks -> tests -> Code review -> goal check -> UAT. At Resolve: preflight -> sync -> checks -> tests -> integration. (The project checks run inside the same preflight call, right after the sync, so they precede the test re-run.) The helper is `node <templates>/trailhead-base-preflight.js --repo <working-root> --config-root <main-checkout> [--sync]` (same three-dir `<templates>` lookup as the commit-msg sync above; `--config-root` is the original checkout the effective config was loaded from, always passed under `worktree`/`clone` so the workspace never re-resolves config). It fetches the trunk (`origin/<trunk>` really advances), picks one base ref, and prints one JSON line `{status, trunk, base, behind, ahead, method?, pulled?, testsRequired, conflicts, checks, checksOk, warnings, message?}`. Run it without `--sync` to measure and with `--sync` to bring the base current.

- **When it runs.** At the **start of Verify** (`build`/`bug`), before the tests, the Code review, the goal check and the UAT, so a rebase never rewrites SHAs a review already cited and the later steps see the synced tree; before the drive-mode ask on the paths that skip Verify (Pending-UAT guard option (a), and a `UAT of:` follow-up); and at Resolve before integrating. Under `git: main` in the shared checkout, right before the trunk push. Under `git: pr` without isolation, on the ticket branch, immediately before the push and PR. Under `worktree`/`clone`, first on the **integration target** (the main checkout, on the trunk, with `--sync`) and then on the ticket branch against it, immediately before the merge or PR. A push rejected as non-fast-forward re-runs the preflight with `--sync`, re-runs the suite, and retries. A Resolve sync that rewrote the ticket's commits (`method: rebase` with `pulled` > 0) leaves the review ledger citing stale SHAs: recompute the ticket diff and re-run the Code review on it before integrating.
- **Reading the status.** Fail closed: only `current` and `synced` (with `checksOk`) let the work go on. `synced` means the base was brought current (`method`: `ff`, `rebase` or `merge`; `pulled` commits) and `testsRequired` is true: re-run the test suite on the synced tree before going on, and a failure loops back to Execute or Fix. `behind` (run without `--sync`) means sync it. `conflict`: stop, name the `conflicts` files, HITL (the helper aborted, the tree is as it was; auto never resolves a merge conflict). `dirty`: commit the work in progress first. `unverified` (the fetch failed, the distance is from local refs): stop and offer a retry or proceeding on local refs knowingly. `trunk-diverged`: the local trunk and `origin/<trunk>` both moved, reconcile the trunk first. `sync-failed` (git refused for another reason, for example an untracked file it would overwrite; the message says which): stop. `error`, `skipped`, a missing helper or a node failure also stop before UAT or integration with a HITL choice; never skip the preflight silently.
- **Project checks.** Failing `checks` (declared in `preflight.checks`, see `configuration-reference.md`, **Preflight checks**) are an acceptance or verify finding: stop before UAT or integration. A `checksError` (invalid declaration) stops the same way.
- **Report.** One result-oriented line, for example: the base was 60 commits behind main: synced, tests re-run, green.

**When a worktree can't build, use `clone`: path-bound tooling.** A worktree isolates *source*, but it is a fresh directory at a new path with no installed dependencies. For a package or submodule whose build/run is **bound to a fixed path** (React Native/Expo, native toolchains, anything with a local `node_modules`, a Metro/bundler cache, or absolute-path config), the code checks out but the app **won't build or UAT from the worktree** without reinstalling and reconfiguring. For those set **`isolation: clone`** (a dedicated clone installs its own deps and runs like the real app), or, if you don't want per-ticket clones, keep **`isolation: none`** and **serialise** that package (one session at a time on it; the other takes a disjoint `Scope:`). Worktree isolation shines where any checkout builds from any path (most libraries, Go/Rust/Python source trees, docs); `clone` is its heavier counterpart for path-bound app toolchains.

**Git submodules force `clone`, never `worktree`.** A submodule is its own repo, gitlink-tracked by the superproject. When a superrepo **has submodules** (a `.gitmodules` file) and isolation is requested, **`isolation: worktree` is escalated to `isolation: clone`**: superproject worktrees share the one real submodule git dir (`.git/modules/<sub>`), so two worktrees that check a submodule out to different commits corrupt each other, whereas a clone gives each ticket a fully independent submodule git dir. Whether a given ticket will *write* a submodule cannot be told up front, so worktree is disallowed outright here rather than allowed-only-if-read-only. `isolation: none` is unchanged (single checkout, overlapping-`Scope:` tickets serialise); the escalation applies whenever isolation would be `worktree`, and the same rule makes the default **`auto`**'s superrepo branch resolve straight to `clone` (see the `auto` bullet above), never `worktree`, for the same reason. Handling is end-to-end:
- **Provision at setup.** Stand the clone up with `git clone --recurse-submodules` (or a follow-up `git submodule update --init --recursive`; nested submodules need `--recursive`), so every submodule the ticket's `Scope:` names is populated and pinned at the superproject's recorded commit **before any build or test runs**. The folder-copy shortcut must bring the submodule working trees too and pass the git-independence check inside each of them (above).
- **Integrate at Resolve, publish before you point.** A submodule change lives in the sub-repo, so commit it **inside the submodule on a branch** (never the default detached HEAD, or the commit is lost when the clone is torn down). A gitlink must **never** reference a commit that exists only in the disposable clone, so **publish the submodule commit first** (push it to the submodule's canonical remote, its configured upstream / `.gitmodules` url; under `git: pr`, open and *merge* the submodule PR), **whatever the isolation mode** (this holds under `none` too, not just per-ticket clones), and **only then bump the superproject gitlink** to that published commit and integrate the superproject per `git:` (`main`, or a PR). **Nested submodules integrate leaf-first:** commit and push the deepest submodule, bump-commit-push its parent's gitlink, up through every level, superproject last. Each commit carries a `Refs:` trailer for this ticket, but a submodule commit is in a **different repo**, so its trailer must be **fully qualified at the superrepo ticket**, `Refs: <owner>/<superrepo>#<n>` (a bare `Refs: #<n>` would resolve against the submodule's own issue tracker); only superproject commits use the bare `Refs: #<n>`.
- **Verify inside each submodule.** Run `git status` **inside every submodule the ticket touched** (nested included), not just the superproject: the superproject only ever shows a submodule as "modified", never that submodule's own dirty working tree. Every submodule path a ticket touches is named in its `Scope:` so setup, integration, and Verify all know which sub-repos to walk.
- **`isolation: none`** is the escape hatch when you want neither per-ticket clones nor the escalation: commit inside the submodule (on a branch) + push it + bump the gitlink in the current checkout, accepting that the submodule then **serialises** across sessions (overlapping `Scope:` holds at claim).

**A ticket that spans two or more submodules.** First ask whether it should be **split**: if the work decomposes into per-submodule pieces wired by a blocker (the gitlink bump waits on the code), prefer that. It stays one ticket only when the change is genuinely atomic across them (a shared contract both sides must adopt together). Then:
- **Commits are coordinated, never one cross-repo commit** (git can't span repos): commit inside each submodule on its branch and **publish it first** (push, or merge its PR under `git: pr`; the objects must exist on a remote before anything durable can point at them), then a **single superproject commit that bumps all the gitlinks together** is the atomic "these versions ship as a set" record. Each submodule commit's `Refs:` is fully qualified at the superrepo ticket (`Refs: <owner>/<superrepo>#<n>`); the superproject commit uses the bare `Refs: #<n>`.
- Its **`Scope:` lists every submodule path it touches**, so the coupling check treats a shared submodule path as overlap and flags a second session touching either one.
- When isolation is requested, the submodules force **`clone`** (worktree is escalated, above), so each touched sub-repo is already independent in the clone; under `none`, work them in the current checkout and accept that each touched submodule serialises against other sessions.

## Pausing & resuming
Switching away from a ticket mid-work (to clear a blocker, chase an urgent bug, or just stop) must not lose the thread.
- **Pause** (`/trailhead:pause [note]`): first commit any work-in-progress (atomic) so nothing is stranded, then post a **`PAUSED`** checkpoint comment: what's done, the exact next step, and any local state (branch, **worktree path under `isolation: worktree`**, how to run it). Then add the `trailhead:paused` label (`gh issue edit <n> --add-label trailhead:paused`, creating it idempotently first, see `substrate-commands.md`) so the pause shows on the tracker and in tooling, after the `PAUSED` comment so a failed comment never leaves a label without a checkpoint. Keep the claim if you'll return soon; **release it** (unassign) if it's open-ended, so someone else can resume; the checkpoint is what makes that safe. If you release, also remove the `.trailhead/session-ticket` marker (SKILL.md Mode 2); if you keep the claim, leave it. Either way, set the work state `--step paused` and keep the file. **If the paused ticket is a `trailhead:whiteboard` quick that has deferred its dashboard refresh to a handoff it is not reaching this session** (born by `quick`, resolution refresh not yet done), refresh the dashboard now (full regeneration from the live tracker) so the unfinished quick shows on the pinned index: the read-only renders never rewrite the dashboard body, so pause is what surfaces it.
- **Resume** (`/trailhead:resume [ticket]`): read the ticket's latest `PAUSED` checkpoint (and the `DISCUSS`/`PLAN` comments above it), then pick up at the recorded next step. Anyone may resume a *released* ticket; a still-claimed one, only its owner. Once that owner check (or the re-claim of a released ticket) has succeeded, remove the label (`gh issue edit <n> --remove-label trailhead:paused`, a no-op when absent); only after the claim is confirmed, so a refused resume leaves the ticket visibly paused. **Re-write the `.trailhead/session-ticket` marker** at the working root (SKILL.md Mode 2 step 2) so the resumed session shows in tooling like the statusline (a released pause removed it), and set the work state to the recorded next step, in the full work-start form (`--map`, `--ticket`, `--title`, `--step <next step>`) so the file is re-created when absent; under `isolation: worktree`/`clone`, also re-enter the ticket's recorded workspace.
- One ticket per session still holds: pausing A to work B ideally means B in a fresh session. If you must switch within one session, checkpoint A first; never leave it half-done and unrecorded.

## Parking & switching between maps
A repo can hold **more than one live map** at once: you park one to work another, or a teammate charts a second and works it concurrently. The mechanics (native sub-issue + per-map `trailhead:map-<n>` label, the scoped frontier, the `.trailhead/active-map` marker, pin policy) are in **SKILL.md → [Multiple maps on one repo]**; this is the operational side.
- **Park a map** = **pause** whatever ticket is in play (`/trailhead:pause`, a `PAUSED` checkpoint, release or keep the claim as usual), then point `.trailhead/active-map` at the other map's number. The parked map needs nothing else: it lives entirely on the Issues, so it waits intact. Resume it later by making it active again and running `/trailhead:work`.
- **Switch to another map** = set `.trailhead/active-map` (or name the map: `/trailhead:map <n>`); the frontier query then scopes to that map's label. `gh issue list --label trailhead:map --state open` lists the live maps if you forget which are open.
- **Two maps, one repo, at the same time**: their frontiers never mix (distinct `trailhead:map-<n>` labels), but they share **one working tree and one git history**. So the [isolation](#isolating-concurrent-sessions) and [undeclared-coupling](#undeclared-coupling-between-parallel-tickets) rules apply **across maps**, not just within one: two in-progress tickets from *different* maps with overlapping `Scope:` still serialise (or want a worktree/clone) exactly as same-map ones do. The `Scope:` check scans in-progress tickets **repo-wide**, not per map.
- **Claiming is unchanged**: the assignee is the claim, per ticket, regardless of which map it belongs to.

## Splitting a ticket
A ticket is sized to one ~100K-token session. When a claimed ticket turns out too big, or fans into distinct pieces, **split it**: don't grind through an oversized ticket. **Splitting is never autonomous.** Whether it was asked for explicitly (`/trailhead:split`) or surfaced mid-work ("this is too big once I'm in it"), **stop and ask the user before creating anything** (the split's shape, which children, is an advisory choice that **offers** the delegate option, per the injection recipe in `choices.md`):
1. **Propose the split and wait for a go-ahead.** Present the children you would create (each one's title and why it's a distinct session-sized piece) and how the original's blockers would re-point, then **wait for the user's confirmation**. Create nothing until they say go: this is a stop-and-ask moment like the rest of the engine's, never the agent's own call. (An explicit `/trailhead:split` is the user asking *to* split, not a go-ahead on *how*: you still propose the decomposition and confirm it.)
2. **Create the child tickets** (create-then-wire): each carries `Parent: <map>`, a `Split from: <original name+link>` line, its type label, the map's `trailhead:map-<n>` label + native sub-issue edge (like any ticket), and `trailhead:blocked` if it has an open blocker. **When children block each other** (B builds on A), wire B's blocker (both the `## Blocked by` line and the native dependency) at the **sibling child's real id (A)**, never at the split-origin: that original is being superseded and closed, so nothing may point at it as a live blocker. Describe A by role if you like, but *link its actual number*.
3. **Supersede the original**: post a comment listing the children (`split into <names+links>`), label it **`trailhead:superseded`**, **drop its native sub-issue edge from the map** (the eager drop at close in `substrate-commands.md`: label first, then the 404-tolerant DELETE, then close, so a slot is reclaimed while the label, `trailhead:map-<n>`, `Parent:` and split-origin links stay intact), and **close it**. The children fully replace it.
4. The superseded ticket stays **out of `Decisions so far`** (it wasn't a decision walked; its children are). If other tickets were blocked by the original, re-point their `## Blocked by` at the relevant child and re-evaluate their `trailhead:blocked`.

Splitting is not resolving: a superseded ticket delivered nothing itself. (If instead the ticket sits beyond the destination, that's *out of scope*, not a split.)

## Undeclared coupling between parallel tickets
Two frontier tickets can be *unblocked of each other* yet still collide: they touch the **same file or seam** with no `## Blocked by` between them. Because build tickets commit **straight to `main`** (or, under `isolation: worktree`, integrate their branch back into it), that collision surfaces as a merge conflict or a logic race, not a caught error; worktree isolation defers *when* it bites (at integration, not mid-edit) but does not remove it. So **at plan time** (once you know the files/seam this ticket touches), scan the other **in-progress** tickets (claimed/assigned, open) and **flag coupling** only when all three hold: same frontier, no declared blocker between them, and a *specific* shared mutable resource (the same file, config key, table/migration, singleton, or seam) that at least one side **writes** (or one produces state the other consumes). On a flag: either wire the blocker (`## Blocked by` + native dependency + `trailhead:blocked`) so one waits, or coordinate with the other claimer and note why it's safe. It's **advisory, never a hard stop**. **Do NOT flag:** both read-only, an already-declared blocker, one clearly downstream of the other, or a vague "same subsystem" with no concrete shared resource.

**Path scope sharpens this (monorepo).** When tickets carry a `Scope:` line (the package/dir(s) they work in, see the ticket anatomy in SKILL.md), use it as the first filter: **disjoint scopes parallelize safely** (two tickets in unrelated packages can't share a file), so the check narrows to tickets whose scopes overlap or that both touch a shared lib / root config. Absent a `Scope:` line, fall back to the file/seam judgement above. Scope is a *hint that rules coupling out fast*, never a guarantee it exists: overlapping scopes still need the shared-writable-resource test before you flag.

**Serialising a scope (`isolation: none`).** This is how you keep two sessions off the same submodule/package when worktrees don't fit (a path-bound app, see the isolation section). Under `isolation: none` the working tree is shared, so **two in-progress tickets whose `Scope:` overlaps cannot run at once**, whatever they touch inside it. So make the scope check a **hold at claim time, not an advisory flag**: right after claiming (before any work), scan the other in-progress tickets' `Scope:` lines; if one **overlaps** this ticket's scope, **stop and tell the user** the scope is busy (name the ticket and its holder), and offer to take a **disjoint-scope** frontier ticket instead or to wait. That overlap-holds-at-claim rule *is* "serialise `app/`": two `Scope: app/` tickets can't proceed together, no extra config needed, and the conventions prose only has to name which scope is serialised for humans. Under `isolation: worktree` or `clone` this reverts to advisory (each ticket has its own workspace), and disjoint scopes always run free (the same-submodule case below is the one overlap `clone` still hard-holds).

**Submodules count as shared scope (superrepo).** Treat **the same submodule path as overlapping scope**, exactly like the same superproject file. Two tickets that touch one submodule contend on its single gitlink tree entry and on the submodule's own shared history, so they **hard-serialise at claim** (a hold, like `isolation: none`), and this **holds even under `clone`**: the escalation gives each ticket an independent submodule *working copy*, but they still integrate to one shared submodule remote and one shared gitlink, so the same-submodule overlap is the one case where `clone` does **not** revert to the advisory-only treatment (unlike disjoint scopes, which run free). Two tickets touching *different* submodules each add a superproject commit that bumps a gitlink; those touch different index paths so git merges them cleanly, but they still **race at superproject push time** (two gitlink-bump commits pushed to `main` concurrently: git rejects the second, which pulls or rebases, re-verifies the gitlink, and retries), so coordinate the gitlink bumps rather than treating different-submodule tickets as needing no coordination at all.

## Concurrent edits to the map
The map issue's **body** is a shared mutable document: two sessions appending to `Decisions so far` at once will clobber each other (GitHub doesn't merge bodies). So:
- **The durable record of a resolution is the ticket's resolution comment**, never the map body. The map's `Decisions so far` is a best-effort index rebuilt from the tickets; if a line is lost to a race, it's recoverable from the closed ticket.
- **Re-read the map body immediately before editing it**, append your one line, write back; keep the window tiny. Never edit the map from stale content read earlier in the session. The default path is the template helper `trailhead-issue-body.js` (found with the same three-dir `<templates>` lookup as `trailhead-work-state.js` below): `node <templates>/trailhead-issue-body.js append --issue <map> --section "Decisions so far" --line "<line>"` does the fail-safe read, re-checks `updatedAt` just before the write (re-applying once on a fresh body if it moved), writes, then runs a post-write check that reports a `conflict` (exit 1, never silent) when a concurrent edit landed in the window; the overwritten text is then in the issue's edit history (the `edited` menu), so re-apply the lost lines from there. The same helper edits any named section (`replace`, `remove`) and the conventions header (`--section :preamble`). This prose is the spec and the fallback: when the helper is missing, do it by hand as described here.
- **Keep map-body writes small and append-only** where possible; heavy restructuring of the map is a single-session job, done when no one else is mid-write.
- Ticket-level state (claim, labels, comments, close) is naturally conflict-free; prefer expressing state there over in the map body.

## Trust & provenance
`trailhead:*` labels drive the map, so they must not be forgeable by outsiders. GitHub already blocks users without write access from applying labels at all; this layer defends against the rest (triage-level collaborators, automations, or a repo that later loosens permissions).

**Trust rule.** Treat a `trailhead:map` / `trailhead:ticket` issue as genuine **only if** every `trailhead:*` label on it was applied by a trusted labeller, *and* (for a ticket) it carries a valid `Parent:` line pointing at this map. A labeller is trusted when it is (a) `github-actions[bot]` (its `GITHUB_TOKEN` events trigger no workflow, so the label guard never runs on them), (b) a login in the `TRAILHEAD_LABEL_ALLOWLIST` repo variable, or (c) a collaborator with write access or above. These are exactly the labellers the label guard never strips, so session and guard agree.

**Provenance per label.** Read the issue timeline (`gh api repos/{owner}/{repo}/issues/{n}/timeline` gives `labeled` events with their `actor`). For every `trailhead:*` label currently on the issue, take the `actor` of its latest `labeled` event; the issue is genuine only when all of those actors are trusted (an earlier rogue event on a since-reapplied label does not count, and one trusted label does not vouch for another). Check an actor in this order: the bot, then the allowlist, then the permission call `gh api repos/{owner}/{repo}/collaborators/{actor}/permission` (`admin`/`write`/`maintain` = trusted; `read`/`none` = not trusted; a `404` or a `none`/`read` answer is a real answer, not a failure). Read the allowlist once per session with `gh variable get TRAILHEAD_LABEL_ALLOWLIST --repo <owner/name>`: `not found` (absent) means empty; any other failure (permission, network) means the allowlist is unknown, not empty. It is comma-separated, entries trimmed, and logins compared case-insensitively, as the guard does.

**Unresolved provenance.** With an unknown allowlist, an actor that is neither the bot nor write+ cannot be judged; the same holds for an actor whose permission lookup failed. Such an issue is held off the frontier and surfaced to the user as "provenance not checkable"; never label it `trailhead:unverified` on a guess.

**On an untrusted match** (a `trailhead:*` issue whose label came from a labeller outside the trusted set, or a ticket with no valid `Parent:`) do **not** put it on the frontier or act on it. Label it **`trailhead:unverified`**, and surface it to the user as a quarantined item to **adopt** (a maintainer re-applies the real labels + wires `Parent:`) or **reject** (strip the `trailhead:*` labels, leave it a normal issue). Never silently trust a label just because it's present.

**Repo-side enforcement (part of first-use setup, not an afterthought).** trailhead **installs the label guard for you**; don't tell the user to copy files. **Every chart or adopt, *check* whether `.github/workflows/trailhead-label-guard.yml` exists** (the first-use repo setup, in SKILL.md's Substrate section); if it's absent, install it, by default on a repo with other collaborators, and as a quick offer on a clearly solo/private one (cheap insurance), but **never silently skip the check**: that's exactly how a repo ends up with trailhead labels and no guard. On go-ahead, write the shipped label-guard template (`${CLAUDE_PLUGIN_ROOT}/templates/trailhead-label-guard.yml` for a plugin install, or `${CLAUDE_CONFIG_DIR:-~/.claude}/trailhead/templates/trailhead-label-guard.yml` for an npm install, take whichever exists) to the repo's `.github/workflows/trailhead-label-guard.yml` and commit it (conventional message; the commit-guard hook keeps it clean). The Action strips any `trailhead:*` label added by a non-write actor and comments why; set an optional `TRAILHEAD_LABEL_ALLOWLIST` repo variable to whitelist extra logins (e.g. a bot trailhead runs as). **Caveat:** pushing a workflow file needs a token with the `workflow` scope; if the push is rejected, run `gh auth refresh -s workflow` and retry (or, as a last resort, tell the user to add the file by hand).

**Keeping the guard current (migration).** The guard filters at **job level** (`jobs.guard.if`: a `trailhead:` label, a sender other than the repo owner, not in `TRAILHEAD_LABEL_ALLOWLIST`), because a skipped job is not billed while a job that starts and returns early from its script costs at least one Actions minute; the in-script permission check stays the real defence. Guards installed before 0.12.1 lack that `if:` and start a runner on **every** label event, which with trailhead labelling all the time runs into thousands of billed runs a month. So whenever the guard is present (every chart/adopt, and after `/trailhead:update`), run `node <templates>/trailhead-label-guard-sync.js --repo <working-root>` (same `<templates>` lookup as the commit-msg sync script below). It prints one JSON status line: `current` (nothing to do), `outdated` (offer the upgrade and always explain why in the question, in plain words: today every label added to an issue starts a run billed at least one minute even when it does nothing, trailhead labels constantly so that adds up to thousands of billed runs a month and can exhaust the Actions minutes, and the updated guard skips irrelevant events before a runner starts with the same protection), `custom` (has the job-level filter but differs from the template: leave it, mention it only if asked), `foreign` (not a trailhead workflow: never touched), `absent` (install as above). On go-ahead for `outdated`, re-run it with `--apply` (it rewrites the file from the template in the working tree only, never a foreign or customised guard), then commit it (`fix: skip trailhead label guard job for irrelevant label events`) and push, with the same `workflow`-scope caveat. The SessionStart hook (or, on a host with no hook bus, the load-first check) also runs it with `--notice` at every session start and surfaces the same upgrade offer until the user answers it; `--ack` records the answer in the gitignored `.trailhead/label-guard-ack` (the guard's hash), so a declined offer comes back only if the file changes. If the script is missing (an outdated install), fall back to reading the file and checking `jobs.guard` for an `if:` containing `startsWith(github.event.label.name, 'trailhead:')`.

**The commit-msg git hook (host-independent commit guard).** On every host trailhead ALSO installs a git **`commit-msg`** hook as a host-independent backstop (a small `sh` wrapper, with its logic installed beside it as `trailhead-commit-msg.cjs`: a `.cjs` is always CommonJS, so a repo whose `package.json` says `"type": "module"` cannot break it; the wrapper never blocks a commit on a startup failure such as node or the `.cjs` missing, and then prints a one-line `trailhead: commit-msg hook inactive (<reason>)` notice to stderr) (defence in depth alongside the host's own `PreToolUse` guard on Claude Code and Codex alike), enforcing the two rules (a Conventional Commits subject of at most 72 chars; never a `Co-Authored-By` trailer) plus, while a `.trailhead/session-ticket` marker is present at the worktree root, a `Refs: #<n>` trailer matching its number, on every `git commit`, whatever host drives it (decision #16). **Every chart or adopt, and at every `work`/`quick` ticket start, run the sync script**: `node <templates>/trailhead-commit-msg-sync.js --repo <working-root>`, where `<templates>` is the first of `${CLAUDE_PLUGIN_ROOT}/templates/`, `${CLAUDE_CONFIG_DIR:-~/.claude}/trailhead/templates/`, `~/.codex/skills/trailhead/templates/` that contains `trailhead-commit-msg-sync.js`: try all three in order, skipping the first when `CLAUDE_PLUGIN_ROOT` is unset or empty (it is often absent from the Bash environment), and never stop at the first miss. It prints one JSON status line and handles every case itself: absent -> installs it; an older trailhead hook (the legacy single-file JS hook, or an outdated wrapper or logic file; recognised by its own header line, not by trusting the filename) -> upgraded in place to the current layout; already current -> left alone; a foreign (non-trailhead) hook -> never touched, only reported (offer to chain it); under a repo's `core.hooksPath`, an existing trailhead hook there is still upgraded in place, but nothing is newly added to that directory. Unlike the label guard, `.git/hooks/` is not version-controlled, so this is a per-clone local install with nothing to commit. **If the sync script is missing (none of the three dirs has it: an outdated install) or node errors, never claim git enforces nothing before looking**: resolve the effective hooks dir with `git -C <working-root> rev-parse --git-path hooks` (resolve a relative output against the working root; it honours `core.hooksPath` and the git common dir shared by linked worktrees), read `<hooks dir>/commit-msg`, and classify it by its header line (a trailhead hook has `# trailhead commit-msg hook (git).` (the `sh` wrapper) or, for the legacy single-file JS hook, `// trailhead commit-msg hook (git).` among its first 5 lines, trimmed; never trust the filename alone; a symlinked `commit-msg` counts as foreign, as the script treats it). The wrapper also needs `<hooks dir>/trailhead-commit-msg.cjs` beside it: without it the wrapper lets every commit through, so treat a missing `.cjs` (or a legacy JS hook, which breaks in `"type": "module"` repos) as present-but-stale: suggest updating the install so the sync script can repair it. Report one result-oriented line: (a) trailhead hook present and executable (`test -x`): git does enforce trailhead's rules here (provided node is on the PATH git runs with; a GUI git client may lack it, and then the wrapper prints the inactive notice on each commit), but its freshness could not be checked or upgraded, so suggest updating the trailhead install; a trailhead hook that is NOT executable: git skips it, so it does not enforce trailhead's rules here (suggest updating the install so the sync script can fix the mode); (b) a foreign hook (or a symlink): left untouched, git does not enforce trailhead's rules here; (c) no hook: git does not enforce trailhead's rules here (suggest updating the install so the sync script can install it). Never blocks the work.

**Work state file (the ticket in play, for tooling).** Alongside the session-ticket marker, trailhead keeps a gitignored `.trailhead/work-state.json` at the working root recording the one ticket in play: `{map, ticket, title, step, auto, autoDone, session, updatedAt}` (`autoDone` is the number of tickets resolved so far in an autonomous run, `0` otherwise). It is independent of `session-ticket` and of the commit-msg hook, and written the same way on Claude Code and Codex by the template helper `trailhead-work-state.js`, found with the same three-dir `<templates>` lookup as the commit-msg sync above (the first of `${CLAUDE_PLUGIN_ROOT}/templates/`, `${CLAUDE_CONFIG_DIR:-~/.claude}/trailhead/templates/`, `~/.codex/skills/trailhead/templates/` that contains it). Forms: `node <templates>/trailhead-work-state.js set --repo <working-root> --map <n|none> --ticket <n> --title "<title>" --step discuss` at work-start (`--map none` for a whiteboard ticket), `node <templates>/trailhead-work-state.js set --repo <working-root> --step <step>` at each step change (`discuss`, `plan`, `execute`, `verify`, `resolve`, `paused`; it merges onto the file, and a different `--ticket` starts it fresh; it needs a ticket on file, so where the file may be absent, as at resume or a pause in a fresh workspace, pass the full work-start form with that step), and `node <templates>/trailhead-work-state.js clear --repo <working-root>` at Resolve, which removes both the work state file and the `.trailhead/session-ticket` marker in one call (each removal attempted independently; it prints `sessionTicket: removed|absent|skipped` next to the usual status). During an autonomous run every `set` adds `--auto true --auto-done <n>`, `n` being the tickets resolved so far in this run. The step-to-state mapping per ticket type lives in `trailhead-work/references/ticket-engines.md`. A missing helper or a non-zero exit is silent and never blocks the work (no user-facing line).
