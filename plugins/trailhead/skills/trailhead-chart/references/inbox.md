# Inbox: triaging issues opened by others

`/trailhead:inbox [issue]` triages issues that aren't trailhead tickets (bug reports, feature requests, questions) and **integrates the worthwhile ones into the map**, keeping the reporter's authorship.

`/trailhead:inbox` presents **four sections**, each named for what it holds. **Present them to the user by these descriptive names, never as a bare letter or "section A/B/C"** (result-oriented output: no internal labels). The four:

**Incoming issues to triage.** Open issues carrying **no** `trailhead:*` label (plus any `trailhead:unverified`, applied by a session under the Trust rule in `../../_shared/teamwork.md`; the guard Action strips labels instead):
```bash
gh issue list --state open --json number,title,author,labels \
  | jq '[.[] | select(([.labels[].name] | any(startswith("trailhead:")) | not) or ([.labels[].name] | any(. == "trailhead:unverified")))]'
```

**Waiting on the reporter.** The open `trailhead:needs-info` issues: ones the maintainer asked a question and parked. They are absent from the incoming query (the `trailhead:*` label drops them), and they come back only when the reporter answers. Read them with the read-only helper, never by hand (a per-issue loop is what goes wrong): `node <templates>/trailhead-inbox-needs-info.js --repo <owner/name> --config-root <project root>`, with `<templates>` found by the same three-dir lookup as `trailhead-work-state.js` (see `../../_shared/teamwork.md`, Work state file). It prints one JSON line `{status, days, answered, timedOut, waiting, unknown, warnings}`: `answered` is an issue whose reporter commented after the label (it wins over the timeout), `timedOut` one with no answer after `days` whole days (`inbox.needs_info_days`, default 14, see `../../_shared/configuration-reference.md`), `waiting` the rest, `unknown` one the helper could not classify (a failed read or a reporter with no usable identity), named with its reason and never offered for closing. Surface `warnings` in one line. Show the answered ones, each proposed for triage by the moves below; the timed-out ones, each offered for closing (see **Needs info**); the still-waiting ones as one count line, no list; and any unknown ones by number and reason. If the helper fails (a missing script, a node error, `status: error`), say the waiting section could not be read and go on with the other sections; never guess which are answered or timed out.

**Parked fog ready to graduate?** The open `trailhead:fog` issues, **most-recently-active first**: recent discussion is exactly where the fog has likely cleared, so you review those, not all of them:
```bash
gh issue list --label trailhead:fog --state open --search "sort:updated-desc"
```
This is **how you notice a fog has cleared**: you don't watch each thread; you run the inbox (as you would to triage new issues), and the parked-fog section surfaces the parked items that moved. For each, decide: **graduate** (adopt in place, see Fog of war), **keep parked** (still vague), or **drop** (turned out out-of-scope/dead → `trailhead:out-of-scope`, drop any native sub-issue edge to reclaim a slot, then close: the eager drop in `../../_shared/substrate-commands.md` is 404-tolerant, so a fog with no edge is a no-op). Optionally, a participant can nudge readiness by commenting on the thread; you confirm at graduation.

**Out-of-scope lines actually deferred?** Scan the map's *Out of scope* section for lines that are **deferred**, not truly ruled out: ones that **name a gate or trigger** (*gated by X*, *quando X*, *dipende da X*), carry a **this-only scope qualifier** (*per questo slice*, *for now*, *in this milestone*, not for the product), describe a **feature wanted later** (already annotated `→ future map`, or plainly still on the roadmap), or **are the gate of an existing `trailhead:seed`**. That last one is a **near-deterministic check**: cross-reference every open `trailhead:seed`'s trigger / `## Blocked by` against the *Out of scope* lines; a line some seed waits on is a **live gate**, so it cannot be "ruled out" and the cluster is **mis-wired** (the gate was left behind), re-route it. A line **decided against for the product** (won't be built, wrong approach, no "for this slice" qualifier) stays put; and a line **already properly parked** (annotated `→ future map` with its dependent seeds wired to a live trigger) is settled, skip it. Only **un-parked** deferred lines surface here. For each deferred line, **ask the user** (never decide silently) how to re-route it, `seed` / `idea` / `todo`, and **which map** it belongs to (this one, or a future / other map), then apply the **out-of-scope-vs-deferred** rules (see `../../_shared/out-of-scope.md`): **re-route the gate first**, tie its dependents to the gate's new form with a **live trigger** (never a dead "ruled out" line), and **move the whole cluster together**. Update or remove the *Out of scope* line to match where each item went (a future-map item stays as an annotated `→ future map` line; an item pulled into this map leaves *Out of scope* entirely).

For each issue in the first three sections (incoming issues, waiting on the reporter, parked fog; for the waiting ones, the answered issues and the timed-out offers), propose a disposition (one of the moves below, with a one-line why) and put them to the user as one list, which they confirm, or amend item by item, before anything is written: every move labels, comments on or closes an issue someone else opened, and an out-of-scope ruling is the human's (`../../_shared/choices.md`). Act only on the user's explicit yes; never close or comment on an issue on your own judgement, and silence or an ambiguous reply leaves it untouched. The moves:

- **Adopt → a ticket.** Integrate it *in place* (same issue number, so the reporter stays credited): append a trailhead block to the body: `Parent: <map name+link>`, `Adopted-from: opened by @<author>`, a reframed `## Question` (the decision/build the *map* will act on), and `## Blocked by`, **without erasing the reporter's original text above it**. Apply `trailhead:ticket` + the right type label (`bug`/`decision`/`build`/`research`/`task`) as a write-access maintainer (which also satisfies Trust & provenance), plus the map's `trailhead:map-<n>` label + native sub-issue edge (like any ticket, so it joins the right map's frontier); add `trailhead:blocked` if it has an open blocker. It lands on the frontier. Comment to the reporter that it's been picked up.
- **Fog.** In scope but not sharp enough to ticket → **keep the issue open and label it `trailhead:fog`** (parked: still visible and tracked, but the `trailhead:*` label drops it out of the inbound query, so it won't re-surface at every triage). Then use the open issue as a **clarification space**: post a comment with the questions that would make it concrete, in the spirit of **Grilling**, but async ("what would *done* look like? which users? where does it show?"), and invite the reporter and anyone interested to refine it in the thread. The fog dissipates through that conversation as much as through other work landing; others can carry the discussion with the reporter without you in the loop. **You don't lose it**: `gh issue list --label trailhead:fog` is the durable list, and the reporter follows their own open issue. When the thread (or the wider work) has made the question sharp, **adopt it in place**: swap `trailhead:fog` for `trailhead:ticket` + the type label, add `Parent:` and the now-answerable `## Question`, and it lands on the frontier: same issue, same reporter, the clarifying discussion preserved above.
- **Out of scope.** Beyond the destination → label `trailhead:out-of-scope`, **drop its native sub-issue edge** to reclaim a slot (the eager drop in `../../_shared/substrate-commands.md`, 404-tolerant, so an un-adopted inbound issue with no edge is a no-op), then close with the why.
- **Duplicate.** In the proposal, name what each one covers (the issue and the existing ticket) and where they differ; only when the existing ticket covers all of it, link it and close. A partial overlap is not a duplicate: link the two and triage the issue by the other moves.
- **Needs info.** Ask the reporter for a repro or specifics; leave it open and park it. Ensure the label exists (`gh label create trailhead:needs-info --color FBCA04 --description "Waiting on the reporter: back in the inbox when they answer" 2>/dev/null || true`), post the question **first**, then add `trailhead:needs-info`. The order matters: when the maintainer is also the reporter, a question posted after the label would count as the answer. The label parks the issue (it drops out of the incoming query) and starts the clock.
  - **Resurfacing.** The issue returns, in the **Waiting on the reporter** section, only when the reporter comments after the label. On an answered issue the moves are the same as for a new issue, each **dropping `trailhead:needs-info` first**. **Ask again** posts the new question, then removes and re-adds the label (two calls: adding a label that is already present makes no event, so the clock would not restart and the issue would resurface on every run). A failed removal leaves the old clock, so it resurfaces next run; a failed re-add leaves it in the incoming queue: both stay visible, and both are reported.
  - **Timeout.** After `days` with no answer the issue is only **offered** for closing, as one more item in the same confirmed list as every other move; it is never closed automatically. On a yes: remove the label, **then** `gh issue close <n> --reason "not planned" --comment "<standard message>"`, in that order (a failed close leaves an open issue back in the incoming queue, visible; a failed removal after the close would leave a reopened issue parked on a stale clock, so a reopened issue is back in the incoming query). The standard message, written in `config.ticket.language`, states when the question was asked and how many days passed, and asks for a new issue linking this one (a reporter without write access cannot reopen an issue a maintainer closed, and a comment on a closed issue would never resurface). **Keep waiting** removes and re-adds the label (two calls, as for Ask again: the label is still present on a timed-out issue, and adding a present label makes no event, so the clock would not restart and the offer would return on every run). A failed removal keeps the old clock, so the offer returns next run; a failed re-add leaves the issue in the incoming queue: both stay visible, and both are reported. Any failed step of a move is reported naming the issue and the state it was left in, with no retry on the user's behalf.
  - **Direct path.** `/trailhead:inbox <n>` on a needs-info issue triages it directly, whatever its state (it is absent from the incoming query), and every move drops the label first.

A rogue issue wearing a `trailhead:*` label it shouldn't (one whose label came from outside the trusted labellers of the Trust rule in `../../_shared/teamwork.md#trust--provenance`, so a label from the bot, an allowlisted login or a write+ collaborator is not rogue; now `trailhead:unverified`) is triaged the same way: **adopt** (a maintainer applies the real labels + `Parent:`) or **reject** (strip the `trailhead:*` labels, leave it a normal inbound issue). Never adopt by trusting a label that was already there; you apply the labels on adoption.
